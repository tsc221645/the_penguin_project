
# ADR-002: Externally hosted, reviewed image assets

- Status: Accepted
- Date: 2026-11-23

## Context

The content specification supersedes the earlier assumption that photographs would be stored under `public/images/`. Third-party photographs must not be downloaded or bundled. The site still needs reliable image attribution, accessible alternatives, credits, and a build-time publishing gate.

## Decision

Store image provenance in the central TypeScript image registry and deliver approved photographs from their external provider. Each image record contains:

- species association and one or more category tags;
- provider and approved image URL;
- optional provider-supported thumbnail URL;
- original file page URL;
- title, creator, TASL attribution text, license, and license URL;
- modifications, alt text, verification date, and review status.

The normal pipeline accepts only verified CC0/public-domain, CC BY 4.0, or CC BY-SA 4.0 material. The validator rejects pending/rejected images, missing provenance, missing alt text, unsupported licenses, and broken species references. The UI links nearby credits to the authoritative source page and generates the `/credits` page from this registry.

The initial approved records use individual Wikimedia Commons file pages and externally hosted Wikimedia URLs. The repository does not bundle those photographs. Local SVG artwork may remain as an unused design asset, but it is not used as a substitute for the required photographic content.

## Consequences

### Positive

- Third-party media rights remain visible and reviewable in source control.
- The repository stays small and avoids redistributing photographs without a reviewed need.
- Provider-native thumbnails can improve loading without guessing URL formats.
- Credits remain consistent across hero, gallery, comparison, and credits contexts.

### Trade-offs

- Images depend on external availability and may require a fallback state.
- Runtime image requests create a third-party privacy and performance consideration.
- A human must periodically review source pages, licenses, and link availability.
- Offline builds can validate metadata but cannot prove that an external URL remains reachable.

## Rejected alternatives

- Bundling downloaded Wikimedia photographs: rejected because the current content requirement explicitly forbids bundling third-party penguin photographs.
- Treating Wikimedia Commons membership or search visibility as permission: rejected because rights must be verified on the individual file page.
- Runtime metadata discovery through an API: rejected because attribution and publishing decisions must remain stable without a runtime API.
